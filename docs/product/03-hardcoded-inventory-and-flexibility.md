# Hardcoded Inventory & Flexibility Audit

Scope: everything hardcoded in `MKTAgent/src` and `MKTAgent/web/src` that a non-engineer would plausibly want to tune, and how to make it configurable. Companion to `01-architecture-techstack-layers.md`. Env vars already validated centrally in `MKTAgent/src/config/env.ts` are called out only where the DEFAULT itself is the problem, not the mechanism — most of `env.ts` is already done right and is noted as a positive baseline, not re-listed row-by-row.

Effort: S = <1hr, M = half-day, L = multi-day (schema/migration or new admin surface).
Priority: P0 = blocks a real buyer/tenant need now, P1 = next quarter, P2 = backlog, P3 = nice-to-have/YAGNI-adjacent.

## Recommended Configuration Architecture

Three tiers, matching what's already partially in place — this audit found the codebase already gets the FIRST tier right almost everywhere (env.ts is a strong, consistent example); the gaps are concentrated in tier 1 items that never got an env var, and in genuine tier-2 gaps (no per-tenant override path exists yet for anything).

1. **Build/deploy-time env vars** (`src/config/env.ts`, zod-validated, fail-fast at boot). Use for: infra endpoints, API keys, feature-flag cron enables, cost/pricing constants, safety ceilings (timeouts, budgets, autonomy caps). This is the existing, correct mechanism — extend it for every P0/P1 item above tagged "env var" rather than inventing a second config system. Concretely: `GEMINI_IMAGE_MODEL`, `GEMINI_TTS_MODEL`, `VEO_PER_SEC_USD`, `TTS_FLAT_USD`, the 8 `*_CRON` schedule strings, `TRIAL_CREDITS`, `VITE_SUPERADMIN_PATH`, `DEFAULT_PLATFORMS`.
2. **Per-tenant DB settings** (new columns/tables on `User`/`Campaign`, or a small `tenant_settings` key-value table for low-traffic knobs). Use for anything that legitimately varies BY CUSTOMER, not by deploy: timezone, default posting window (already a column — just needs a real per-tenant default instead of a hardcoded fallback), TTS voice preference, lead-scoring criteria hand-edit (structure already exists via `LeadScoringCriteria`, just needs a UI + persistence path), lead hot/warm/cold thresholds. Do not build a generic "settings framework" up front (YAGNI) — add typed columns as each concrete need is confirmed, following the pattern `Campaign.postingWindow`/`Campaign.timezone` already established.
3. **Per-run overrides** (already the dominant pattern via `GoalSpec` slots, `qualityPref`, `dropPlatforms`, campaign-strategist slot count from NL parsing). This tier is in good shape — the NL-parsing fallback-with-override pattern in `deterministic-analyzer.ts` (duration/cadence) is a good model to replicate for anything currently only overridable via chat text and not a form field.

**Deliberately NOT making configurable (YAGNI)** — and why:
- **Agent persona prose / prompt template bodies** (§1, §Prompts): moving ~1000+ lines of reviewed, test-covered prompt/persona text into external template files trades type-safety and code-review coverage for a "non-engineer can edit prompts" capability nobody has asked for yet. Revisit only on a concrete request for tenant-specific agent personas.
- **Data Guard / summarize chunk window sizes** (40k/20k chars): these are Gemini-context-window engineering tradeoffs, not business rules — a non-engineer tuning them wrong silently degrades quality or cost with no visible symptom until it's already wrong.
- **Retry attempts/backoff, rate-limit floor**: reliability engineering knobs with sensible shared defaults; per-call-site overrides already exist where genuinely needed (e.g. `connector-runtime.ts` explicit `attempts: 3`). Adding an env var per of ~30 call sites is pure surface area for no real benefit.
- **`SocialPlatform`/`MessagingChannel` as free-text instead of enums**: a new platform ALWAYS needs a bespoke adapter (auth flow, payload shape, rate limits differ per platform) — no config value alone makes a new platform work. The enum + migration friction correctly reflects real engineering cost; the fix is a documented runbook (§4), not removing the type safety.
- **Local filesystem cache paths**: not a flexibility gap today (single-instance deploy); premature to add config for a scaling scenario that doesn't exist yet.
